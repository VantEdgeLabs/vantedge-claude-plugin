Building agent apps on VantEdge

The end-to-end developer guide: scaffold an app with the SDK, run it on your local minikube cluster, then ship the same image to the dev and prod EKS clusters — all through the CLI.

vantedge-client-python vantedge SDK Temporal runtime

Who this is for. Developers building code-first agent apps — durable workflows, scheduled pollers, streaming or one-shot jobs — that read and write your workspace's data through the context router, and optionally serve their own web UI. You write Python against the vantedge SDK; the vantedge-cli deploys it as a sandboxed worker.

The mental model

Two tools, two planes, two credentials. Internalize this picture and everything else follows.

  • The SDK (vantedge) is what your app is written against. It provides the Temporal runtime (a generic worker), the context_router data client, and the schedule helpers. Your app is just a Python module that exports WORKFLOWS / ACTIVITIES / SCHEDULES.
  • The CLI (vantedge-cli) is your control-plane tool. It scaffolds app repos, builds & deploys them, and lets you start / observe / stop runs. It only ever talks to one thing: the platform backend.

You handle the API key. The workspace token is minted and injected automatically — you rarely touch it.

Prerequisites & install

Two pip packages: the CLI (to deploy) and the SDK (to author + run locally).

# Control-plane CLI
pip install vantedge-client            # or: pip install -e .  from a checkout
vantedge-cli --help

# The SDK, for authoring & running a worker locally
pip install "vantedge[runtime]"        # pulls temporalio
pip install "vantedge[runtime,web]"    # add FastAPI/uvicorn if your app serves a UI

For local development you also need: Docker (build images), access to the minikube cluster (*.vantedge.run via mkcert), and the mkcert root CA trusted (below).

Getting your credentials

1 · An API key sk_live_

The API key authenticates the CLI to the backend as your user within your org. Create one from the dashboard (it calls POST /api/external/api-keys/, authenticated by your Clerk session). The raw key is shown once — copy it immediately.

  • Format: sk_live_… (production) or sk_test_…. ~256 bits of entropy; the backend stores only a hash.
  • It resolves to a user + organization. Deploy authorization uses that org: you can only deploy into workspaces your org owns.
  • Optional workspace scoping is supported, but a normal control-plane key is org-wide.
export VANTEDGE_API_KEY=sk_live_xxxxxxxxxxxxxxxx

2 · A workspace workspace_id

Apps deploy into a workspace. Create a workspace in the dashboard; its integer id is the workspace_id you pass to deploy (e.g. 4). A workspace belongs to your org and carries its own connectors (data sources) and its own context router — which is what your app reaches through the data plane.

One workspace = one tenant. The workspace_id flows everywhere: the task queue is ws-<workspace_id>, the namespace is app-<workspace_id>-<name>, and the minted wst_ token is scoped to exactly that workspace.

3 · Point the CLI at a backend + trust the CA

export VANTEDGE_PLATFORM_URL=https://minikube-api.vantedge.run   # which environment (see §Deploy)
# Local mkcert cluster: trust the root so TLS verification stays ON
export VANTEDGE_TLS_CA_BUNDLE="$(mkcert -CAROOT)/rootCA.pem"

--insecure is a last resort. It disables verification entirely. Prefer --ca-bundle / VANTEDGE_TLS_CA_BUNDLE; in prod behind a real cert, use neither.

Scaffold a new app

vantedge-cli init writes a complete, deployable repo — a real durable workflow, its Dockerfile, manifest, and deps.

vantedge-cli init myapp             # a worker app
vantedge-cli init myapp --web       # also scaffold a web UI kit

The app-module contract

The runtime imports one module (VANTEDGE_APP_MODULE, default app) and discovers Temporal objects from these top-level names:

NameShapeRequired
WORKFLOWSlist of @workflow.defn classesone of WORKFLOWS/ACTIVITIES
ACTIVITIESlist of @activity.defn functionsone of WORKFLOWS/ACTIVITIES
SCHEDULESlist[ScheduledWorkflow]optional

If you omit the lists, the module is auto-scanned for decorated classes/functions — but being explicit is clearer. The scaffolded app.py:

"""A durable workflow that answers a question by querying your data."""
from datetime import timedelta
from temporalio import activity, workflow


@activity.defn
async def run_query(sql: str) -> dict:
    # Side effects belong in activities. Import the client HERE (not at module
    # top) to keep the workflow sandbox import-clean.
    from vantedge.tools import context_router
    return await context_router.query(sql)


@workflow.defn
class AnalystWorkflow:
    @workflow.run
    async def run(self, sql: str) -> dict:
        return await workflow.execute_activity(
            run_query, sql, start_to_close_timeout=timedelta(seconds=60),
        )


WORKFLOWS = [AnalystWorkflow]
ACTIVITIES = [run_query]

The one rule that bites everyone. Import context_router (and anything doing network / file I/O) inside the activity, never at module top. Temporal re-imports your module inside a deterministic workflow sandbox; an eager import that touches urllib trips the sandbox. The vantedge package is passed through the sandbox automatically; add others via VANTEDGE_PASSTHROUGH_MODULES.

Reading & writing data — the context_router client

from vantedge.tools import context_router gives your activities a governed data client. It reads VANTEDGE_API_URL + VANTEDGE_WORKSPACE_TOKEN (injected by the platform) and POSTs to the backend data proxy — your app never holds router credentials.

CallDoes
await context_router.query(sql, *, data_sources=None)Run a vetted read query, return rows.
await context_router.execute(sql, …)Run a write (DML).
await context_router.ask(question, …)NL → SQL → rows.
await context_router.sources() · schema(source)List connectors / inspect a schema.
await context_router.action(source, name, **args)Invoke a connector action (stored procedure).
await context_router.mark_as_read(source, message_id)Example connector write action.

Scheduling

Export a SCHEDULES list of ScheduledWorkflow. The runtime registers them as Temporal Schedules on boot (idempotent — safe across restarts and replicas).

from vantedge.runtime.schedules import ScheduledWorkflow

SCHEDULES = [
    ScheduledWorkflow("myapp-poll", AnalystWorkflow, every="60s"),
    # every: "60s" | "5m" | "1h" | "2d" | seconds | timedelta
    # cron="*/5 * * * *" takes precedence over every; arg=
]

Develop locally on minikube

The default deploy path is server-side build — no local Docker or registry access needed. Just vantedge-cli deploy myapp 4 and the platform builds the image on its own builder and deploys the digest. This works the same locally as on dev/prod once the CLI is pointed at minikube (VANTEDGE_PLATFORM_URL).

export VANTEDGE_API_KEY=sk_live_xxxx
export VANTEDGE_PLATFORM_URL=https://minikube-api.vantedge.run
export VANTEDGE_TLS_CA_BUNDLE="$(mkcert -CAROOT)/rootCA.pem"

cd myapp
# Default: server-side build + deploy. No local Docker required.
vantedge-cli deploy myapp 4

The local-build escape hatch (--local-build) still exists for offline/CI/air-gapped work where you want to build with your own docker buildx and push to a registry the cluster can pull from. Locally on minikube, the wrinkle is that you push to minikube-registry.vantedge.run but in-cluster nodes pull via localhost:5000:

cd myapp
# Escape hatch: build+push LOCALLY, then deploy.
vantedge-cli deploy myapp 4 --local-build \
  --push-image minikube-registry.vantedge.run/myapp:0.1.0 \
  --image      localhost:5000/myapp:0.1.0 \
  --base-image minikube-registry.vantedge.run/vantedge-app-base:0.5.5
  • --local-build — build with docker buildx and push to --push-image instead of the default server-side path.
  • --push-image — the host-facing tag the CLI pushes to (minikube registry).
  • --image — how the node pulls it (localhost:5000/… locally). If your push and pull endpoints are the same (ECR), pass --image alone.
  • --base-image — the base runtime your Dockerfile builds FROM. Locally, point at the minikube-registry base; on dev/prod it defaults to the ECR base.
  • --allow-internet open sandbox egress (e.g. an app calling a third-party service like Twilio; LLM calls don't need this — they route through gateway.llm) · --dry-run preview without provisioning · --verbose show raw docker build logs + full JSON response.
  • Web UI, env vars, secrets, egress allowlist, output delivery → all declared in vantedge.yaml, not deploy flags.

Building the local base image. The base image lives in the SDK repo and must exist in the minikube registry before an app can build FROM it locally:

cd vantedge-sdk && docker/base/build.sh  →  pushes minikube-registry.vantedge.run/vantedge-app-base:<pyproject version>. The same tag is published to ECR by CI for dev/prod (see next section).

Iterate. Edit app.py and re-run vantedge-cli deploy myapp 4. Redeploys are idempotent (ArgoCD upsert). Preview a run without touching the cluster with --dry-run, which prints the minted token, namespace, task queue, and full ArgoCD spec.

You can also run the worker on your laptop (no cluster) against a workspace token:

cp .env.example .env          # fill VANTEDGE_API_URL + VANTEDGE_WORKSPACE_TOKEN + TEMPORAL_*
python -m vantedge.runtime.worker

Deploy to the EKS clusters (dev → prod)

The key insight. An app is always deployed into the same cluster its backend/ArgoCD runs in — the ArgoCD destination is the in-cluster API server, hard-wired. There is no per-app cluster flag. So which environment you deploy to is decided by which backend the CLI points at (VANTEDGE_PLATFORM_URL) and which registry your --image names.

Deploying to dev/prod is the same command with two differences:

# DEV EKS
export VANTEDGE_PLATFORM_URL=https://dev-api.vantedge.run
vantedge-cli deploy myapp 4 \
  --image 997334016349.dkr.ecr.us-east-1.amazonaws.com/myapp:0.1.0

# PROD EKS — point at the prod backend, same image already in ECR
export VANTEDGE_PLATFORM_URL=https://api.vantedge.run
vantedge-cli deploy myapp 4 \
  --image 997334016349.dkr.ecr.us-east-1.amazonaws.com/myapp:0.1.0
  1. Registry. Dev/prod nodes pull from ECR, not the minikube registry. Build & push your app image to ECR (or let CI do it), then reference that repo in --image. There's no registry-selection logic — the image string is the whole story.
  2. Base image. The vantedge-app-base image is published to ECR by the SDK repo's GitHub Actions workflow on merge to main/develop (tag = the pyproject.toml version). The scaffolded Dockerfile defaults its ARG BASE_IMAGE to the ECR base, so dev/prod builds "just work"; locally you override with --base-image.

Registries are independent. The minikube registry and ECR never sync. The version tag is the shared contract: build the same tag into each registry from the same Dockerfile so local and prod are byte-identical. For the base image, CI owns the ECR side; docker/base/build.sh owns the local side.

Observe & control runs

vantedge-cli start myapp --workflow AnalystWorkflow --input "SELECT 1"
vantedge-cli runs 4 --app myapp --status Running
vantedge-cli run  <workflow_id>            # current state
vantedge-cli history <workflow_id>         # event timeline
vantedge-cli logs myapp --tail 200
vantedge-cli terminate <workflow_id> --reason "done"

For deep inspection — full history, pending activities, retries, signals — use the Temporal Web UI for the environment (e.g. minikube-temporal.vantedge.run). Schedules, child workflows, and their fan-out are all visible there.

Worked example: Tracey — an autonomous deal-flow analyst

Tracey is a real app on this platform. It watches a shared Outlook inbox for inbound pitch decks, analyzes each deck with an LLM against an investment thesis, writes a CRM lead + a PDF report, marks the email read, and serves a fund-management dashboard. It exercises every feature in this guide: a schedule, a poller that fans out child workflows, activities that read/write data through the context router, a connector write-action, a persistent store, and a web UI.

The app module (shape)

from vantedge.runtime.schedules import ScheduledWorkflow

@activity.defn
async def find_unread_deals(source: str) -> list[dict]:
    from vantedge.tools import context_router
    return await context_router.query(
        'SELECT id, subject, "from_emailAddress_address" AS sender '
        'FROM ...users_outlook_email_messages '
        'WHERE "isRead" IS false AND "hasAttachments" IS true')

@activity.defn
async def parse_deal(deal: dict) -> dict: ...        # resolve attachment, LLM vision on the deck
@activity.defn
def  enrich_deal(...): ...                            # thesis enrichment
@activity.defn
def  evaluate_deal(...): ...                          # score vs strike zone
@activity.defn
def  format_deal(...): ...                            # -> GraphiteVCAnalysis (pydantic)
@activity.defn
def  store_result(rec: dict) -> None: ...            # write to PVC-backed sqlite
@activity.defn
async def mark_read(deal: dict) -> None:             # connector WRITE action
    from vantedge.tools import context_router
    await context_router.mark_as_read("office365", deal["message_id"])

@workflow.defn
class DealAnalysisWorkflow:                           # one deal, end-to-end
    @workflow.run
    async def run(self, deal: dict) -> dict: ...

@workflow.defn
class PollInboxWorkflow:                              # lists unread, fans out a child per deal
    @workflow.run
    async def run(self) -> int: ...                  # child id deal-<mid>, dedup + ABANDON

WORKFLOWS = [DealAnalysisWorkflow, PollInboxWorkflow]
ACTIVITIES = [find_unread_deals, parse_deal, enrich_deal, evaluate_deal,
              format_deal, store_result, mark_read]
SCHEDULES  = [ScheduledWorkflow("tracey-poll-inbox", PollInboxWorkflow, every="60s")]

Deploy it (local minikube)

# Default (server-side build, no local Docker needed):
vantedge-cli deploy tracey 4 --allow-internet

# Escape hatch (local buildx to minikube registry, if you need it):
vantedge-cli deploy tracey 4 --local-build \
  --build-context ./tracey \
  --push-image minikube-registry.vantedge.run/tracey:0.2.4 \
  --image      localhost:5000/tracey:0.2.4 \
  --base-image minikube-registry.vantedge.run/vantedge-app-base:0.5.5 \
  --allow-internet

Web UI is enabled by web.enabled: true in vantedge.yaml — served at <dashboard-host>/apps/4/tracey/. --allow-internet lets the app reach the fund's third-party HTTPS endpoints (LLM calls don't need this — they go through gateway.llm). The schedule starts firing immediately — watch the poller and its per-deal children appear in the Temporal UI, and processed deals show up on the Leads screen. To ship to dev/prod: push tracey to ECR, point at that backend, drop the local-only flags.

Troubleshooting

SymptomCause / fix
Could not connect … certificateLocal mkcert CA not trusted — set VANTEDGE_TLS_CA_BUNDLE (preferred) or --insecure.
HTTP 401Missing/invalid API key. Check VANTEDGE_API_KEY (sk_live_…).
Workspace not found in your organizationThe workspace_id isn't owned by your key's org.
Pod ImagePullBackOffNode can't pull. Locally use the localhost:5000/… reference in --image; on EKS use the ECR repo the cluster can pull.
Base image manifest unknownThe vantedge-app-base tag isn't in this registry. Build it locally (docker/base/build.sh) or wait for the SDK CI to publish it to ECR.
RestrictedWorkflowAccessError / sandbox import errorYou imported a network/IO module at module top. Move it inside the activity, or add it to VANTEDGE_PASSTHROUGH_MODULES.
TEMPORAL_TASK_QUEUE unsetRunning the worker locally without env — copy .env.example and set the TEMPORAL_* vars.
Data call raises VANTEDGE_API_URL/…_WORKSPACE_TOKEN is not setIn-cluster these are injected at deploy. Locally, set them in .env.
App can't reach its LLM / the internetSandbox egress is closed by default — deploy with --allow-internet.
